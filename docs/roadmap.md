# ROADMAP: Notion 포트폴리오 쇼케이스 (진행 중)

> **이 문서의 역할**: `docs/roadmap.md`는 **현재 진행 중이거나 예정된** 개발 로드맵을 관리하는 메인 문서(살아있는 문서)입니다.
> 하나의 버전이 완료되면 이 문서의 내용을 `docs/roadmaps/roadmap_vN.md`로 아카이브하고, 이 문서는 다음 버전(V+1)의 계획으로 새로 채웁니다.
>
> - MVP(V1)는 이미 완료되어 [`docs/roadmaps/ROADMAP_v1.md`](./roadmaps/ROADMAP_v1.md)에 아카이브되어 있습니다. (수정 금지 — 과거 기록 보존용)
> - 지금 이 문서는 **V2** 계획을 다룹니다. 이번 갱신(2026-07-29)은 5가지 요구사항(아래 "검토 항목 개요")을 반영해 V2 범위를 대폭 재검토/확장한 버전입니다.

> ⚠️ 참고: 이 프로젝트는 Next.js 16 기반이며 학습 데이터 상의 관례와 다른 breaking change가 있을 수 있습니다.
> `AGENTS.md`는 App Router 라우팅/데이터 페칭 코드 작성 전 `node_modules/next/dist/docs/`를 확인하라고 안내하지만, **이 경로는 실제로 존재하지 않음이 `shrimp-rules.md`에서 이미 확인됨**. 대신 `context7` MCP로 Next.js 16 공식 문서를 조회한다.
> 이번 갱신에서 `context7`(`/vercel/next.js/v16.2.9`)로 재확인한 중요 breaking change: **Next.js 16에서는 `middleware.ts`가 `proxy.ts`로 이름이 바뀌었다** (인증/접근 제어를 다루는 4단계에 직접 영향).

## 버전 관리 규칙

- 이 저장소의 로드맵은 `docs/roadmap.md`(현재 진행 중) + `docs/roadmaps/roadmap_vN.md`(완료된 과거 버전) 구조로 관리합니다.
- **아카이브 시점**: 한 버전(V2, V3, ...)의 모든 핵심 단계가 완료 기준을 충족하면, 그 시점의 `docs/roadmap.md` 내용을 `docs/roadmaps/roadmap_v{N}.md`로 복사/이동하고, `docs/roadmap.md`는 다음 버전 계획으로 새로 작성합니다.
- 파일명 규칙: 기존 MVP는 `ROADMAP_v1.md`(대문자)로 이미 존재하므로 그대로 유지하고, V2부터는 소문자 `roadmap_v2.md`, `roadmap_v3.md`, ... 형식을 사용합니다.
- `CLAUDE.md`의 "개발 로드맵" 참조는 항상 `docs/roadmap.md`(현재 버전)를 가리키도록 고정합니다. 과거 버전을 찾을 때는 `docs/roadmaps/` 디렉터리를 확인하면 됩니다.

## 현재 목표 (V2)

MVP(V1)에서 Out of Scope로 명시했던 기능 중 **프로젝트 상세 페이지**를 축으로, 사용자가 이번에 확정한 5가지 요구사항을 반영해 V2 범위를 재구성합니다. MVP에서 구축한 Notion 연동 레이어(`lib/notion.ts`), 타입(`types/project.ts`), 카드/필터 컴포넌트(`components/project-card.tsx`, `components/tag-filter.tsx`) 등 기존 자산을 최대한 재사용하는 것을 원칙으로 합니다.

### 검토 항목 개요 (사용자 확정 원문 기준)

1. **프로젝트 상세 페이지 뎁스 구조** — 문제 정의/목표/과정/결과로 구성된 케이스 스터디 페이지.
2. **관리자 Dashboard** — 프로젝트 상태/콘텐츠/업데이트 현황을 확인하는 관리자용 대시보드.
3. **프로젝트/콘텐츠 CMS 구조 개선** — Notion 기반 CMS를 확장 가능한 구조로 개선(케이스 스터디 콘텐츠 저장 방식 포함).
4. **프로젝트 필터링** — 프로젝트 증가 시 탐색성을 높이는 카테고리/태그 기반 필터링.
5. **포트폴리오 목적에 맞는 추가 고도화 기능 제안** — 사용자 원문: *"추가로 포트폴리오 웹사이트라는 목적을 고려해서 필요한 고도화 기능이 있다면 우선순위와 함께 제안해줘."* (최초 전달 시 문장이 잘려 "사용자 확인 필요"로 임시 표기했으나, 이후 코디네이터를 통해 원문 전체를 확인함 — 아래 4단계에서 정식 제안으로 다룸)

## 0단계: CMS 구조 확장 방향 결정 (요구사항 3)

### 배경
1단계(케이스 스터디: 문제 정의/목표/과정/결과)를 구현하려면 Notion 쪽에 "본문 콘텐츠를 어디에 담을지"부터 결정해야 합니다. 현재 `types/project.ts`의 `Project`에는 본문 필드가 전혀 없고, `lib/notion.ts`는 속성(property) 기반 파싱만 합니다. 이 결정은 1단계뿐 아니라(케이스 스터디 저장 방식), 필요 시 4단계 필터링의 "카테고리/태그 분리" 논의와도 연결됩니다.

### 옵션별 트레이드오프

| 옵션 | 저장 위치 | 난이도 | 장점 | 단점 |
|---|---|---|---|---|
| A. 속성(property) 확장 | Notion DB에 "문제정의/목표/과정/결과" 4개 Rich Text 속성 추가 | 하 | `lib/notion.ts`의 기존 파싱 패턴(`getPlainText` 등) 그대로 재사용, 구조가 명확히 고정됨 | Notion 속성 패널은 서식(이미지/리스트/헤딩)이 자유롭지 않아 "케이스 스터디"라는 서사적 콘텐츠엔 표현력이 부족함. 속성 개수가 늘어나면 Notion DB 테이블 뷰가 복잡해짐 |
| B. 페이지 본문 블록 | 프로젝트 페이지 자체 본문에 헤딩(H2: 문제 정의/목표/과정/결과)으로 구분해 자유 작성, `notion.blocks.children.list()`로 조회 | 상 | 이미지/리스트/임베드 등 자유로운 서식 가능. - **카테고리/태그 분리**: 4단계(필터링 고도화)에서 다시 다룹니다.

## 1단계: 프로젝트 상세 페이지 — 케이스 스터디 구조 (요구사항 1 + 5-A)

> 0단계 결정(케이스 스터디 저장 방식)에 의존합니다. 아래 내용은 기존 V2 검토(라우팅/단건조회/카드클릭/캐싱)를 유지하면서, 이번 요청의 "문제 정의/목표/과정/결과" 케이스 스터디 구조를 통합한 것입니다.

### 코드 기준 재확인 (2026-07-29)
`lib/notion.ts`는 `resolveDataSourceId()` → `notion.dataSources.query()` → `parseProject()` 흐름만 존재하고 단건 조회 함수는 없음. `types/project.ts`의 `Project`에는 본문 필드가 없음. `components/project-card.tsx`는 카드 전체를 `<a href={project.link} target="_blank">`로 감싸되, **`project.link`가 `null`이면 앵커 없이 `cardBody`만 반환**함(59~61행).

### 하위 항목 (Must/Should/Could · 난이도 · 영향 범위)

| 하위 항목 | 분류 | 난이도 | 영향 범위 |
|---|---|---|---|
| 라우팅 (동적 라우트 신설) | Must | 중 | `app/` 신규 파일만 추가, 기존 파일 영향 없음 |
| 단건 조회 함수 (`getProjectById`) | Must | 하 | `lib/notion.ts` 추가만, 기존 `getPublishedProjects()` 무변경 |
| 케이스 스터디 4섹션(문제정의/목표/과정/결과) 렌더링 | **Must** (이번 요청으로 격상 — 기존 로드맵의 "본문 콘텐츠 Could"에서 승격) | 0단계 선택지에 따라 하(A)~상(B) | 0단계 선택에 따라 `types/project.ts`/`lib/notion.ts`/신규 렌더러까지 |
| 카드 클릭 동작 결정 | Must | 선택지별 하~중 (아래 표 참고) | `components/project-card.tsx` |
| 404/비공개 처리 | Must | 하 | 신규 `page.tsx` 내부 로직만 |
| 캐싱 전략(`revalidate`) | Should | 하 | 신규 `page.tsx`에 export 한 줄 추가 |
| 타입 확장 | Should (0단계 결정에 종속) | 하 | `types/project.ts` |
| 프로젝트별 동적 메타데이터/OG (요구사항 5-A) | Should | 메타데이터 자체는 하, 동적 OG 이미지 생성은 중~상 | 신규 `app/projects/[id]/` 내 `generateMetadata()`, (선택) `opengraph-image` 파일 컨벤션 |

### 할 일
- **라우팅**: 프로젝트별 상세 페이지 라우트 신설 (예: `app/projects/[id]/page.tsx`).
  - `context7`(`v16.2.9`) 확인 결과 `params`는 `Promise<{ id: string }>`이며 `await params`로 꺼내는 패턴, `notFound()`, 페이지별 `revalidate` export는 표준으로 유지됨. `shrimp-rules.md` 규칙대로 페이지 props 타입은 직접 정의하지 말고 `PageProps<'/projects/[id]'>` 전역 헬퍼를 사용한다.
  - `app/**/page.tsx`는 컴포넌트 컨벤션 예외 대상이므로 `export default async function`을 유지한다.
- **데이터 조회**: `lib/notion.ts`에 단건 조회 함수 추가 (`getProjectById(id)`). 기존 파싱 로직(`parseProject`, `getThumbnailUrl`, `getPlainText`)을 재사용하고, `notion.pages.retrieve({ page_id: id })` + `isFullPage()` 가드 기반으로 구현. 목록 조회와 달리 `resolveDataSourceId()`가 필요 없어 목록 조회보다 오히려 더 단순함.
- **케이스 스터디 콘텐츠 렌더링**: 0단계에서 확정한 저장 방식(A/B/C)에 따라 문제 정의/목표/과정/결과 4개 섹션을 상세 페이지에 순서대로 배치.
  - 옵션 A라면 4개 Rich Text 속성을 각각 섹션 제목 + 본문으로 렌더링(난이도 하).
  - 옵션 B라면 `notion.blocks.children.list()`로 페이지 본문을 가져와 헤딩 기준으로 섹션을 나누고, 블록 타입별 렌더러(문단/이미지/리스트/헤딩 등)를 구현(난이도 상).
  - 어느 옵션이든 "결과" 섹션에는 가능하면 정량적 임팩트(성과 지표, 사용자 수, 성능 개선 폭 등)를 강조하는 것을 콘텐츠 작성 가이드로 권장(요구사항 5의 "설득력" 목적과 직결, 별도 기능이 아니라 콘텐츠 가이드로 흡수).
- **카드 클릭 동작 결정**: 기존 분석 유지 — (a) 카드 클릭 → 상세 페이지, 외부 링크는 상세 페이지 내 버튼으로 이동(난이도 중, MVP 클릭 동작 재정의) / (b) 카드 클릭은 기존처럼 외부 링크 유지, 상세 페이지는 별도 진입점(난이도 하, 회귀 없음) / (c) 둘 다 지원(난이도 중, 마크업 재구성 필요). `project.link`가 `null`인 카드의 처리도 함께 결정 필요. → **사용자 결정 필요**, 난이도·회귀 위험 종합 시 (b)를 우선 권장.
- **캐싱 전략**: `app/page.tsx`의 `revalidate = 600`을 상세 페이지에도 적용할지 검토. 옵션 B(블록 조회) 채택 시 API 호출이 하나 더 늘어나므로 캐싱 값 재검토 여지 있음.
- **동적 메타데이터/OG (5-A)**: 현재 `app/layout.tsx`는 전역 정적 OG 메타데이터만 갖고 있어(코드 확인됨), 상세 페이지가 SNS/메신저로 공유돼도 어떤 프로젝트인지 구분되지 않음. 상세 페이지에 `generateMetadata()`로 프로젝트별 title/description을 반영하고, 여유가 있으면 `opengraph-image` 파일 컨벤션으로 썸네일 기반 OG 이미지를 생성. 채용 담당자/클라이언트에게 링크를 공유할 때의 설득력에 직접 영향을 주는 항목.
- **404/비공개 처리**: `notFound()`(from `next/navigation`)를 서버 컴포넌트에서 조건부 호출하는 표준 패턴 사용(v16.2.9 기준 유효 확인).

## 2단계: 필터링 고도화 (요구사항 4 — 신규 기능 아님, 기존 개선)

### 코드 기준 재확인 (2026-07-29) — 재정의의 근거
`components/tag-filter.tsx`와 `components/project-showcase.tsx`를 직접 확인한 결과, **이미 다중 태그 선택 + OR 조건 필터링이 구현되어 있습니다** (`ProjectShowcase`의 `selected` 배열 상태, `projects.filter((p) => p.tags.some((tag) => selected.includes(tag)))`). 즉 "단일 태그만 가능"하다는 흔한 한계는 이미 없는 상태입니다. 따라서 이번 요구사항은 **신규 필터링 기능 개발이 아니라, 기존 `TagFilter`/`ProjectShowcase`의 잔여 한계를 개선하는 작업**으로 재정의합니다.

확인된 잔여 한계:
1. 카테고리와 태그의 구분이 없음 — PRD의 "태그"(Multi-select) 필드 하나에 기술 스택/카테고리가 뒤섞여 있음.
2. 태그 간 AND 조건(교집합)이 불가능 — 현재는 OR(합집합)만 지원.
3. 필터 상태가 URL에 반영되지 않음 — 새로고침/공유 시 필터 선택이 유지되지 않음(클라이언트 `useState`로만 관리).
4. 태그별 프로젝트 개수 표시가 없음 — 몇 개나 매칭되는지 미리 알 수 없음.
5. 모든 필터링이 클라이언트에서 이미 로드된 전체 목록을 대상으로 처리됨 — 현재 규모(V1 검증 시점 기준 Notion DB 항목 0건)에서는 문제 없으나, 프로젝트 수가 크게 늘어나면 재검토 필요.

### Must/Should/Could 및 영향 범위

| 하위 항목 | 분류 | 난이도 | 영향 범위 |
|---|---|---|---|
| 카테고리/태그 필드 분리 | Should (0단계 CMS 논의와 연동, 사용자 확인 필요) | 중 (Notion 신규 속성 1개) | `docs/PRD.md`, `types/project.ts`, `lib/notion.ts`, `components/tag-filter.tsx` |

| 태그별 프로젝트 개수 뱃지 | Could | 하 | `components/tag-filter.tsx` |

### 왜 이 순서인가
0단계/1단계와 데이터 의존성이 없어 병행 진행이 가능합니다. 다만 "카테고리/태그 분리"는 0단계에서 다루는 Notion 스키마 결정과 같은 성격의 작업이므로 그 논의와 묶어 처리하는 것이 효율적입니다. 프로젝트 수가 현재 매우 적은 상태(V1 검증 시점 0건)이므로 "탐색성" 문제 자체가 아직 실증되지 않았다는 점을 감안해, 서버 사이드 필터링 전환 등 규모 대응 작업은 향후 후보로 내렸습니다.

## 4단계: 관리자 Dashboard (요구사항 2 — 비판적 검토, 범위 축소 권장)

### PRD와의 긴장 관계 (반드시 먼저 짚어야 할 지점)
`docs/PRD.md`의 CMS 선택 이유는 명시적으로 **"Notion API를 활용하여 비개발자도 콘텐츠 관리 가능 (재배포 없이 Notion에서 프로젝트 추가·수정·태그 변경 가능)"**입니다. 즉 "콘텐츠 관리 UI"는 이미 Notion 자체로 해결하도록 설계되어 있습니다. 별도 관리자 대시보드를 만든다면, 그것이 Notion과 다른 어떤 가치를 제공하는지 반드시 구분해야 합니다.

- **쓰기 가능한 CRUD 관리 도구** (프로젝트 추가/수정/발행 상태 변경 등을 대시보드에서 직접 수행): PRD의 "Notion = CMS" 전제와 정면으로 중복됩니다. Notion에 이미 있는 기능을 재구현하는 것이며, 추가로 다음 문제가 발생합니다.
  - **인증/인가 필요**: `context7`(`/vercel/next.js/v16.2.9`) 확인 결과, Next.js 16에서는 미들웨어 파일명이 `middleware.ts` → **`proxy.ts`**로 변경되었습니다. 세션 쿠키 기반 인증(`decrypt(cookie)` 후 `NextResponse.redirect`), 또는 역할 기반 접근 제어(`next/navigation`의 `forbidden()`) 패턴이 공식 문서에 존재하지만, 이 프로젝트에는 현재 인증 라이브러리/세션 저장소가 전혀 없습니다(코드 확인: `package.json`에 auth 관련 의존성 없음, `proxy.ts`/`middleware.ts` 파일 없음).
  - **동기화 문제**: 대시보드에서 쓴 값과 Notion 원본 사이의 동기화(둘 중 어느 쪽이 "진실의 원천"인지), 동시 편집 충돌 등 새로운 복잡도가 생깁니다.
  - **보안 위험**: 쓰기 API를 외부에 노출하면 공개 배포된 개인 포트폴리오 사이트치고는 과도한 공격 표면이 생깁니다.
  - → **작업 원칙("새로운 기능보다 기존 구조 개선 우선") 및 이번 검토 결과, 쓰기 가능 CRUD 관리 도구는 이 프로젝트 규모/목적에 비해 과잉설계로 판단해 로드맵에서 제외를 권장합니다.**

- **읽기 전용 요약 대시보드** (예: 전체 프로젝트 발행 상태 한눈에 보기, 썸네일/링크 누락 경고, 마지막 수정 시각, 태그별 분포 통계 등): Notion 자체의 테이블/보드 뷰로도 상당 부분 커버되지만, "이 사이트에 지금 무엇이 노출되고 있는가"를 웹에서 바로 확인하고 싶은 경우엔 나름의 가치가 있습니다. 다만 이 경우에도 **비공개(`공개여부=false`) 프로젝트 데이터를 화면에 노출**하게 되므로(`shrimp-rules.md` 8절: "클라이언트 컴포넌트에서 비공개 프로젝트 데이터를 필터링하는 것 금지" — 즉 비공개 데이터 자체가 서버 밖으로 나가면 안 된다는 원칙과 맞닿아 있음), **최소한의 접근 제어**(예: 단일 소유자용 공유 비밀 토큰을 `proxy.ts`에서 검사하는 수준)는 필요합니다. 다인증/회원 시스템까지는 필요 없습니다.

### Must/Should/Could 및 영향 범위

| 하위 항목 | 분류 | 난이도 | 영향 범위 |
|---|---|---|---|
| 쓰기 가능 CRUD 관리 도구 | **비권장 (로드맵 제외 권장)** | 상 (인증/보안/동기화 포함) | `proxy.ts`(신규), 세션/인증 레이어(신규), `lib/notion.ts` 쓰기 함수(신규), 광범위 |
| 읽기 전용 발행 현황 요약 대시보드 | Could (축소된 형태로만) | 중 (경량 접근 제어 포함) | 신규 `app/admin/` 라우트, `lib/notion.ts`에 전체 조회 함수 추가(비공개 포함), `proxy.ts`(경량 토큰 검사) |

### 왜 이 순서인가
4개 항목 중 PRD의 근본 설계와 가장 크게 충돌할 소지가 있고, 인증/보안이라는 이 프로젝트에 없는 새로운 축을 요구하므로 우선순위를 가장 낮게 배치했습니다. 진행 여부와 범위(읽기 전용 한정)는 **사용자 확인 후** 착수합니다.

### 완료 기준 (진행하기로 확정한 경우에만 적용)
- [ ] 대시보드 범위가 "읽기 전용 요약"으로 확정됨 (쓰기 가능 CRUD는 채택하지 않음)
- [ ] 대시보드 접근에 최소한의 접근 제어(`proxy.ts` 기반 토큰/비밀번호 검사)가 적용됨
- [ ] 대시보드가 발행 상태/썸네일·링크 누락/태그 분포 등 유의미한 요약 정보를 제공함
- [ ] 비공개 프로젝트 데이터가 인증되지 않은 경로로 노출되지 않음
